# herdr-agent-state

Reports this pane's agent state to [herdr](https://herdr.dev), the terminal
multiplexer that draws an agent indicator beside a pane's title. PiG builds it as
an ordinary Go factory extension: no tools, no commands, no renderers - four
event handlers that turn the session's lifecycle into two herdr reports.

Outside a herdr pane the extension is inert. It registers its identity and
nothing else, opens no socket and writes nothing.

This source is not selected by the `pig-with-batteries` manifest yet. Load it
directly with `pig -e ./herdr-agent-state`, or add a Piglet extension entry for
it, which is the step that makes it part of a composition.

## Provenance and licensing

Ported from the extension herdr installs into every Pi session,
`~/.pi/agent/extensions/herdr-agent-state.ts`, whose header records
`HERDR_INTEGRATION_ID=pi` and `HERDR_INTEGRATION_VERSION=9`. That file is
regenerated by herdr whenever its Pi integration changes, which is why the port
is reviewed here instead of patched in place. The wire contract - environment
variables, RPC methods, parameter keys, socket protocol - was taken from herdr's
published documentation, "Add Herdr support to your agent" and the socket API
reference, so it does not depend on that file staying unchanged. Herdr's server
source is not public, so a maintainer with herdr's source should confirm the two
identity values below.

The Go code in this directory is original work under this repository's MIT
license. It is a reimplementation, not a copy: the behaviour follows herdr's
documented protocol. Its runtime dependency is a herdr daemon speaking that
protocol; herdr itself is not vendored, redistributed or required at build time.
If a reviewer considers the port derivative of herdr's integration file, that is
a licensing question for the maintainer to settle, and it is raised here rather
than assumed away.

## Runtime requirements

- PiG whose SDK exposes the surface this extension compiles against: the PiG
  validator commit pinned in `.github/workflows/ci.yml` (PiG 0.2.0,
  `35280def`), verified with `pig install --validate-only`.
- A herdr daemon, with the pane started by herdr so the process inherits
  `HERDR_ENV=1`, `HERDR_SOCKET_PATH` and `HERDR_PANE_ID`.
- An interactive `tui` session. RPC, JSON and print modes have no pane to
  display, and RPC still reports `hasUI=true`, so the run mode is the gate.

The transport is herdr's, not Pi's: the same socket and the same two methods,
`pane.report_agent_session` and `pane.report_agent`, one newline-terminated JSON
request per connection, answered with at least one byte.

Two identity values are deliberately **not** the ones herdr's Pi integration
sends, because herdr attributes a pane's agent state to a `(source, agent)` pair
and reserves one of them:

| Wire value | Value sent | Why |
| --- | --- | --- |
| `source` | `piglet:herdr-agent-state` | herdr's own integrations use the `herdr:` prefix, and its documentation tells a third party not to. Reporting as `herdr:pi` is accepted at the API layer and then discarded: herdr reserves that source for the authority it already holds over Pi. |
| `agent` | `pig` | This is the name users see, and herdr tells an integration to use its own agent's name rather than one herdr already supports. `pi` would also collide with herdr's built-in Pi agent. |

Verified against a running herdr 0.9.3: with `source: herdr:pi, agent: pi` the
report answered `{"type":"ok"}` and the pane stayed `agent_status: unknown`; with
the values above, `herdr pane get` and `herdr agent list` show the pane as agent
`pig`.

## What it reports

`session_start` claims the pane: it publishes the session reference herdr needs
(`agent_session_path`, or `agent_session_id` for an in-memory session) and the
first state. From then on the pane is `working` between `agent_start` and
`agent_settled`, and `idle` otherwise. A repeated state is not resent, and every
report carries a strictly increasing `seq`, because herdr rejects a report that
goes backwards.

Two gates keep a headless session silent, matching herdr's Pi integration:

- `HERDR_ENV=1` plus a socket path and pane id, which herdr sets only in panes
  it launched;
- run mode `tui`, because RPC, JSON and print modes have no pane to display and
  RPC still reports `hasUI=true`.

### Not reported here: `blocked`

herdr's protocol has a third state, `blocked`, for a pane waiting on the user,
with a message explaining the wait. Two things are needed for it, and this
repository's PiG has neither.

A producer. herdr's own integrations only *listen* for the notification; the
producer is a second file, a Claude Code style command-hook file, whose matchers
map `PreToolUse` on an `AskUserQuestion` tool to `blocked`. PiG rejects that
declaration outright: `coding/hookconfig/hookconfig.go` fails
`parse <path>: PreToolUse is not supported by Pig`, and its supported hook events
are exactly `SessionStart`, `PostToolUse`, `Stop` and `SessionEnd`. There is no
`AskUserQuestion` tool either - PiG's builtin set is bash, content, edit, fd,
find, grep, ls, read, rg, ripgrep, write - so the matcher has nothing to match.

A channel. The listener needs the `pi.events` bus. PiG main has it
(`Extension.Events()`), but the PiG revision this repository's CI pins does not,
neither in its SDK nor in its host, and that SDK's `callHost` is unexported, so a
Go extension built against it cannot reach `events.on` or `events.emit` even by
hand.

So this build reports `idle` and `working` only. Nothing is lost quietly: herdr
keeps treating those normally, and restoring `blocked` needs two upstream changes
rather than one, namely `PreToolUse` hook support or an equivalent agent-side
signal, and a PiG revision whose SDK exposes the event bus. Until then the honest
mapping is the one used here.

## Delivery

Handlers only enqueue. One worker owns the queue, so reports arrive in order and
only one socket is in flight; each report gets one attempt bounded at 500 ms and
one retry bounded at 1500 ms, for a pane that reconnects while herdr restarts.
A queued state report is superseded by the next one, because herdr asks an
integration to send only the latest state and drop older ones. `session_shutdown`
drains the queue, bounded at two seconds, so the last state reaches herdr instead
of dying with the extension process.

A report herdr refused is written to stderr, which PiG collects as the
extension's output, and it names the cause instead of dropping it - a missing
socket, a refused connection and silence at the deadline are different bugs that
look identical from the outside:

```text
herdr-agent-state: herdr did not accept pane.report_agent after 2 attempt(s) in 0s: dial /run/user/1000/herdr/herdr.sock: connect: no such file or directory
```

Nothing is shown in the transcript and the agent never waits on herdr.

Deliberate differences from the TypeScript original:

- `source` and `agent` are PiG's own identity, not herdr's `herdr:pi` / `pi`
  (see the table above).
- `blocked` is not reported, for the reason given above.
- Delivery is owned, cancellable and drained work rather than fire-and-forget
  promises, as PiG's extension contract requires; the TypeScript version could
  race its `reportSession()` against the first state report after `agent_start`,
  and here the session report is always ordered first.
- A refused report is logged instead of silently dropped, so a herdr that never
  hears about a pane is diagnosable.
- Pane state is guarded by a mutex, because PiG dispatches every inbound handler
  on its own goroutine while Pi runs its handlers on one thread.

## Windows

Herdr publishes a named pipe on Windows and a Unix socket elsewhere;
`dial_windows.go` opens the pipe path and `dial_unix.go` dials the socket. The
Windows path compiles (`GOOS=windows go build ./...`) but is not exercised by
this repository's Linux build target.

## Check it by hand

Validate the source, which builds it against the staged SDK and starts it once:

```sh
pig install ./herdr-agent-state --validate-only --json
```

Watch the wire with a socket that answers like herdr does:

```python
# fake-herdr.py
import json, os, socket, threading
path, log = "/tmp/herdr.sock", "/tmp/herdr-received.jsonl"
os.path.exists(path) and os.unlink(path)
server = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM); server.bind(path); server.listen(16)
def handle(conn):
    with conn, open(log, "a") as out:
        buffer = b""
        while b"\n" not in buffer:
            chunk = conn.recv(4096)
            if not chunk:
                return
            buffer += chunk
        out.write(json.dumps(json.loads(buffer.split(b"\n")[0]), sort_keys=True) + "\n")
        conn.sendall(b"ok\n")
while True:
    connection, _ = server.accept()
    threading.Thread(target=handle, args=(connection,), daemon=True).start()
```

```sh
python3 fake-herdr.py &
HERDR_ENV=1 HERDR_SOCKET_PATH=/tmp/herdr.sock HERDR_PANE_ID=1 \
  pig -e ./herdr-agent-state
```

Starting a session reports the session and `idle`; a prompt reports `working` and
then `idle`. The same run with `--print` reports nothing, which is the mode gate
working. The log file holds one line per report. Remove the socket when finished.

Against a real herdr, check what herdr thinks:

```sh
herdr pane get "$HERDR_PANE_ID"     # agent: pig, agent_status: idle
herdr agent list                    # this pane listed with agent "pig"
```

If herdr shows no agent for the pane, the report did not arrive or was discarded.
The refusal line above names the first case; the identity table above explains
the second, which is what a report sent as `herdr:pi` or `agent: pi` hits.
