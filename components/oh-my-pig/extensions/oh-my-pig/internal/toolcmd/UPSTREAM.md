## Execution & security model vs omp

- **Single execution path**: every mounted and special tool runs strictly through PiG's host `Context.ExecuteTool` (so PiG's JSON Schema validation, `tool_call`/`tool_result` hooks, permission gates, `tool_execution_*` events, nested-call records, and `Details` all run).
- **Per-call revocable credential**: one loopback TCP listener (`127.0.0.1:0`) runs per session (closed on `lifecycle.End(sessionID)` / `session_shutdown`). Each `PreambleWithRelease(ctx)` mints a fresh 192-bit random hex token bound to that single bash call's `sdk.Context` and cancellation signal, and revokes it as soon as the bash call finishes (for `Preamble(ctx)`, revocation is bound to `ctx.Done()`). The token is stored in an unexported shell variable (`__omp_tc_token`) so child processes do not inherit it in their environment; the sourced preamble file unlinks itself immediately via `BASH_SOURCE[0]`; `__omp_tc_call` runs in a subshell body with `set +x +v` silenced so `set -x` never prints the token or internal frames and caller FD 8/9 are never clobbered; `command -p` bypasses hostile `PATH` entries for `base64`/`tr`/`openssl`/`rm`.
- **Threat-model comparison with omp**: omp embeds its shell in-process, so external programs started by a bash command have no network endpoint or credential at all. Because PiG runs real OS `bash` child processes, a same-user process cannot guess the 192-bit token or reuse a revoked token after the bash call finishes, and child processes do not inherit the token in their environment or on disk after sourcing; however, code executing *inside* the bash shell itself (e.g. `set` / `echo "$__omp_tc_token"` in the model's own bash command) or a same-user debugger/ptrace process inspecting the bash process memory while a bash call is actively in flight can read the live call's token until that call ends.
- **Harness-internal `i` (intent) field**: mounted tools share a single wire schema with top-level calls where `internal/intent` injects a top-level string property `i` (often `required`, or inside each branch of a pure `anyOf`/`oneOf` root) and strips it before `Execute`. Without importing `internal/intent`, `toolcmd` decides from the schema alone: `i` is omitted from `--help`, flag parsing (`--i` is rejected as an unknown flag), required-flag checks, and prompt docs/catalog; when the schema defines top-level `i` (including across every non-null branch of a pure `anyOf`/`oneOf` root), `RunToolCli` injects `"i": ""` into the arguments passed to `Context.ExecuteTool` so host validation passes, and never adds `i` when the schema does not define it. **Known limitation**: a tool whose own schema legitimately defines a top-level argument named `i` cannot be distinguished from harness-injected `i` from the schema alone (none of oh-my-pig's built-in tools defines an `i` argument; set it via `-j '{"i":...}'` only if a future third-party tool ever needed it, though `RunToolCli` currently overwrites `args["i"] = ""`).
- **Dispatch recording (`details.toolCommands`)**: every tool command executed on either path (`TryDirectWithOptions`/`TryDirect` using `ctx.ToolCallID()`, or the loopback bridge using `bashToolCallID` carried on the per-call `callGrant` minted by `PreambleWithRelease`) records one `DispatchRecord` in invocation order in the session's per-session table, drained and cleared by `DrainDispatches(ctx sdk.Context) []map[string]any` (returning `nil` when empty). Wire shape matches omp's `ToolCommandDispatch` (`tool`, `mode`, `exitCode`, optional `args` with `github` `pr_create` projection and harness-injected `i` stripped, optional `inner` from `outcome.Result.Details` omitted when nil or empty `{}`), plus `callId` carrying the nested `ExecuteTool` call's own ID (`outcome.ToolCall.ID`, distinct from the outer bash call ID per PiG `coding/nested_tool_calls.go:260-275`) so `checkpoint` can locate the nested result entry (omp's `ToolCommandDispatch` has no `callId` field). Records for an aborted bash call that never drains are dropped when its grant is released (`release()`), and any remaining session buckets are released on `lifecycle.End(sessionID)` / `session_shutdown`. Integrator wiring: `shell.ToolCommandDispatches = toolcmd.DrainDispatches`.
- **Direct-call fallback for mounted tools (`resolveFallbackTool`) via `PrepareLoadout` / `HiddenDeclarations`**: in omp (`sdk.ts:4301-4324, 5228`, `tools/tool-commands.ts:237-254`, `agent-loop.ts:2975-2994`), mounted tools are omitted from advertised provider `tools`, yet a direct model tool call to `lsp`/`debug`/`ast_edit`/etc. still resolves and executes through `resolveFallbackTool`, while special commands (`resolve`, `reject`, `propose`, `report_issue`) are NOT fallback-resolved (`Tool <name> not found` on direct call; reachable only via bash). To match omp on every PiG provider without any payload filter, `toolcmd.syncSession` keeps enabled **mounted** tools in PiG's active tool list (so `agent/tool_execution.go:366` dispatches direct calls through PiG's full validation/hook/execution pipeline) and keeps **special** commands inactive while the transport is on (still reachable from bash via `ExecuteTool` on codemode/deferred exposure). `toolcmd.PrepareLoadout` (wired by integrator to `shell.PrepareLoadout` on the `bash` tool definition) returns `ToolLoadoutChanges{HiddenDeclarations: ...}` derived from `loadout.Declared` + exposures + mountable registry, so PiG's `Session.hideDeclarations` (`coding/session_loadout.go:288-327`, `coding/session.go:566`) omits mounted tool declarations from the transcript projection before ANY provider converts messages (Anthropic messages + `tool_addition` + cache breakpoints on last kept tool, OpenAI Completions, OpenAI Responses + `additional_tools`, Google Gemini/Vertex, AWS Bedrock, pi-messages, faux) and passes them in `hiddenTools`. `toolcmd.AdvertisedTools(ctx, active)` is exported for prompt/eval/modes consumers.
- **Active tool order (`BUILTIN_TOOLS` vs explicit lists), explicit top-level pinning, external deactivation, & conditional built-ins (`RegisterAutoActivate`)**: at `session_start` only (when no turn is in flight and nothing has been declared yet), `syncSession` evaluates `RegisterAutoActivate(name, enabled)` entries (e.g. `find` from `internal/search` when `find.enabled: "on"` or a native judge is already available at startup) when no explicit caller list is set, and orders `keptActive` by omp's `BUILTIN_TOOLS` order (`tools/index.ts:622-652`, matching `read, bash, edit, eval, glob, grep, [find,] task, wait, todo, web_search, write` for the default advertised set). When `ExplicitToolOrder(ctx)` returns a non-empty list (e.g. subagent frontmatter `tools:` such as `reviewer`'s `read, find, grep, glob, bash, lsp, web_search, ast_grep`), caller order is preserved, explicitly listed built-ins stay **top-level** (never mounted as bash commands and never hidden by `PrepareLoadout`, matching omp's `mountBuiltinTools = requestedTools === undefined` in `tools/index.ts:930-938` and `sdk.ts:4747-4754, 4835-4838`), and unlisted mountables are never activated. Across subsequent turns, `syncSession` tracks tools it activated per session (`managedActive` / `externallyDeactivated`) and never re-activates a mountable or codemode/deferred tool that a user tool picker or another extension deactivated, restoring it only if its area setting flips `false -> true` (mirroring omp's `SessionTools.#enabledToolNames` / `reconcileBuiltinTools`, `session/session-tools.ts:1557, 2554-2577`). Because PiG's `planToolLoadout` (`coding/session_loadout.go:178-189`) unconditionally keeps already-active tools ahead of newly added names and appends new names to the end, `syncSession` clears with `SetActiveTools([]string{})` ONLY at `fromSessionStart` when `needsActiveToolReorder` is true, and never issues an empty `SetActiveTools([])` reset after `session_start`.
- **Unknown-tool suggestions (`SuggestToolName` / `EventContext`)**: ports omp's `suggestToolNames` and `formatToolNotFoundMessage` (`packages/agent/src/agent-loop.ts:2996-3069`, `sdk.ts:4327, 5229`: trailing `__` and `_` segments ≥ 3 chars, longest tail first, advertised tools ahead of mounted fallback names, capped at 3). `toolcmd.Register` installs a `sdk.EventContext` handler that rewrites PiG's bare `Tool <name> not found` error `toolResult` messages in place (preserving `_pigContextUnchanged: true`) so the model receives omp's exact `Did you mean <tool>?` / `Closest available: ...` text on the next turn.

## Not ported

| Feature | Reason |
|---|---|
| Embedded shell engine builtins (`omp_shell::SessionCommands`) and reach from `timeout`, `xargs`, `env`, `find -exec`, `bash -c`, `command <tool>` | PiG's `internal/shell` spawns real OS `bash` child processes rather than embedding omp's Rust shell. Shell functions defined by `Preamble`/`PreambleWithRelease` are callable in pipelines, subshells, and `&&`/`;` chains inside the bash shell, but external executables (`xargs`, `timeout`, `env`, `find -exec`, nested `bash -c`) and `command <tool>` cannot invoke bash shell functions. |
| Plain POSIX `sh` (dash/ash) and `zsh` without `/dev/tcp` | Plain `sh` lacks built-in TCP redirection, and inline `zsh/net/tcp` `>&$fd` syntax in `bash -c` arguments triggers macOS endpoint-security SIGKILL. `internal/shell` prefers `bash` (which supports `/dev/tcp` on macOS 3.2+, Linux 4/5, and Windows Git Bash); non-bash shells fail cleanly with exit 127 and an explicit stderr message. |
| Windows native `cmd.exe` / PowerShell transport | `internal/shell` targets Git Bash / MSYS2 (`bash.exe`) on Windows; `preamble_windows.go` compiles cleanly, sends `pwd -W` for native Windows paths, runs under Git Bash `/dev/tcp`, or exits 127 with a clear message if `/dev/tcp` is unavailable. |
| Live-streaming partial `toolCommands` progress updates during a running bash call (`ToolCommandRecorder.progress`) | Final `details.toolCommands` (and `details.toolCommandsSole` in `internal/shell`) are recorded on both direct and bridge paths and drained via `DrainDispatches(ctx)` when the bash call completes; mid-execution partial `inner` progress frames are not streamed to `OnUpdate`. |
| Explicit CLI `--tools` presentation pinning (`presentationPinnedToolNames`) | Subagents with explicit frontmatter `tools:` (wired via `ExplicitToolOrder`) pin listed built-ins top-level as in omp (`tools/index.ts:930-938`). For top-level CLI `--tools`, PiG's `sdk.Context` does not expose whether a tool was explicitly pinned on the command line, so a top-level `--tools lsp,bash` session will still mount `lsp` if `tools.commands` is true and `lsp` is enabled. |
| Third-party extension tools registered with default `direct` exposure | In omp, extension/custom tools with omitted `loadMode` default to `"discoverable"` and mount as bash commands. In PiG, deactivating a `ToolExposureDirect` tool removes it from `callableEntriesLocked`, making `Context.ExecuteTool` reject it as unknown (`coding/session_loadout.go:111-127`). `internal/toolcmd` therefore mounts only `ToolExposureCodemode`/`ToolExposureDeferred` tools and keeps `direct` third-party extension tools top-level so they remain callable. |
| `pty: true` refusal for lines invoking tool commands (`invokedToolCommand` in `bash.ts:1900-1905`) | `internal/toolcmd` exports non-executing `InvokedCommand(ctx, command) (name, ok)` over the same parser as `TryDirect` plus compound segment scanning so `internal/shell` can refuse `pty: true` before executing any tool or spawning a shell. |
| Background jobs / services outliving their issuing bash run | In omp, session commands fail with status 1 once their `Shell::run` ends (`crates/shell/src/commands.rs:30-32`). With `PreambleWithRelease`, revoking the grant when the bash call finishes enforces the same rule for foreground runs; async jobs and services that keep their grant until the job/service exits can invoke tool commands while running (revoked on completion/stop). |
| Appending full `--help` text to schema validation failures (`validateToolCommandArgs` in `tool-commands.ts:417`) | `ParseToolArgs` catches CLI syntax, type, enum, and missing-required errors with exit 2 and `run \`<tool> --help\``; deeper JSON Schema validation (e.g. raw `-j` payload type mismatches) runs in PiG's host inside `Context.ExecuteTool`, which returns its own validation error text without appending `--help`. |
| Full `Bun.Glob` feature set (`[...]`, `**`, `!` negation) in `tools.commandInline` | `globMatch` supports `*`, `?`, and `{a,b}` brace groups (covering omp's documented patterns like `mcp__context_mode_*`); character classes, `**`, and leading `!` negation are not implemented because tool command names are flat identifiers without path separators. |
| Terminal image (Kitty graphics) encoding for image tool results (`encodeTerminalImage`) | `internal/shell` does not decode Kitty graphics frames back into `sdk.ToolResult` image blocks; text stdout/stderr and exit codes are bridged. |
| Approval-tier / prewalk / ACP permission decorator (`resolveToolTier`, `decorateExecution`, `mcpReadOnlyHint`) | PiG's extension SDK does not expose omp's prewalk coordinator or ACP permission decorator; PiG's host `tool_call`/`tool_result` hooks run automatically on every `Context.ExecuteTool` call. |
| `tools.commandNotices` mount/unmount UI notices | UI notification toast when dynamic MCP/extension tools mount or unmount is omitted; the model still sees updated mounts on the next turn via `PromptDocs` / `before_agent_start` / `mcp_servers_change`. |
| Eval bridge direct-call policy (`withEvalBridgeToolCall` / `isEvalBridgeToolCallable`) | `internal/eval` owns the eval tool bridge in oh-my-pig. |
| Lenient schema-repair validation (`lenientArgValidation`) | PiG's host runs standard JSON Schema validation inside `Context.ExecuteTool`; no lenient-validation bypass flag exists on `sdk.ToolInfo`. |
| Distinguishing a tool-owned argument literally named `i` from harness-injected intent `i` | Because `internal/toolcmd` does not import `internal/intent` and mounted tools share one schema with top-level calls where `internal/intent` injects `i` (with configurable `PI_INTENT_DESC` or bare description), `toolcmd` treats any top-level `i` property (including in every non-null branch of a pure `anyOf`/`oneOf` root) as harness-internal. None of oh-my-pig's built-in tools defines its own `i` parameter. |
| Persisted transcript / JSON `tool_execution_end` text for unknown-tool `Did you mean <tool>?` suggestions (`agent-loop.ts:3019-3069`, `sdk.ts:5229`) | **Model-facing text is ported** via `toolcmd.SuggestToolName` + `sdk.EventContext` in-place rewrite (`suggest.go`), so the model reads omp's exact `Did you mean <tool>?` / `Closest available: ...` text on the next turn. Only the host-emitted `tool_execution_end` JSON event and persisted session entry remain PiG's bare `"Tool <name> not found"` because PiG's `agent/tool_execution.go:366-369` returns an immediate error result before any extension `tool_call`/`tool_result` hook runs. |
| Explicit CLI `--tools` order without `ExplicitToolOrder` wiring | PiG's `sdk.Context` does not expose whether the user passed an explicit `--tools` CLI list or its requested order; `ExplicitToolOrder` handles caller-supplied explicit lists (e.g. subagent frontmatter from `internal/agents`), while top-level `--tools` sessions sort built-ins into `BUILTIN_TOOLS` order at `session_start`. |
| Mixed `tools.commands` across two concurrent sessions with identical declared tool sets in one process | `sdk.ToolPrepareLoadoutFunc` receives no `sdk.Context`/session ID. `PrepareLoadout` derives hidden names directly from `loadout.Declared` and resolves `tools.commands` across live sessions by matching declared sets; only when two live sessions in the same process have identical declared tool sets AND opposite `tools.commands` values is the hook ambiguous (defaults to hiding mounted codemode/deferred tools). |
| Mid-session positional insertion of newly activated built-ins (e.g. `find` enabled mid-session on `model_select`) | PiG's `planToolLoadout` (`coding/session_loadout.go:178-189`) treats `SetActiveTools` as a set: already-active tools always keep their existing order and newly activated tools are appended at the end; no atomic `SetActiveToolsOrdered` / insert-at-index API exists on the host (and `ai/transcript.go:251-278` also preserves first-declared order across deltas). Conditional built-ins enabled at startup (e.g. `find.enabled: "on"`) use `RegisterAutoActivate` to land at their exact `BUILTIN_TOOLS` position at `session_start`; tools activated mid-session after a turn append at the end. |
| `BashToolDetails.toolCommands[]` / `toolCommandsSole` field differences (`tier`, `callId`, `toolCommandsSole`) | Compared with omp's `ToolCommandDispatch` (`tools/tool-commands.ts:100-122`): `tier` (and `readOnlyHint`) are omitted because PiG has no prewalk coordinator (`prewalk.ts:74-76`); `callId` is added per record carrying the nested `ExecuteTool` call ID (`outcome.ToolCall.ID`, PiG `coding/nested_tool_calls.go:260-275`) for correlation; `details.toolCommandsSole` is attached by `internal/shell` for `internal/ansi/native_run.go:238` (omp computes `isSoleInvocation` inside `packages/tui/src/tools/bash.ts:596-632`). Empty `{}` `inner` details are omitted to match omp. |
