Workload e (perf.py large_turns): one prompt, 100 scripted model requests (99 tool turns + final text) -> 200-message conversation; six `read` of a 48 KB text file,
three `read` of 180x180 noise PNGs (97 KB), two 100 KB assistant texts; the provider payload grows to about 1 MB (43 MB of before_provider_request payloads in total);
tracing on with mockls. The extension subscribes to before_agent_start, turn_start, before_provider_request, message_end, tool_execution_*, turn_end, agent_end, agent_settled, session_*.

Result (n=1, profiled run, so overhead included): extension CPU 5.41 s of which
  sdk.(*Extension).handleArmedRequest 44% -> sdk/json.Unmarshal 41%; sdk.(*conn).readLoop -> json.UnmarshalFrame 35% = checkValid 33% (a full validation scan: stateInString/skip) + unmarshal;
  decodeState.objectInterface/unquote/literalInterface (the any-tree) ~25%.
  port code (serializeForTracing/buildMultipart/appendValue): ~5% CPU.
Allocation 1.05 GB total (alloc_space): sdk/json.appendString 21% (port serialisation path), jsontext.Value.UnmarshalJSON 19% (frame copy), conn.readFrame 19% (frame buffer),
  json.unquote 19% + unquoteBytes 9% + objectInterface 8% (the any-tree) => the SDK decode path is ~56% of allocations.
Unprofiled, same machine, interleaved with TS-in-pig (smoke n=1): work_ms 5344 (go) vs 3252 (ts) vs 1900 (pi); ext CPU 4730 vs 3050 ms.
Proposal: do not run checkValid on a frame the host framed itself; avoid the second copy of the frame (readFrame then jsontext.Value); consider exposing raw JSON for event payloads.
